```bash
sudo tcpdump -i any port 80 -c 10
```

**Послідовність прапорців перших трьох пакетів**

| № | Напрямок          | Прапорці в tcpdump | Назва   | Що відбувається                                                 |
|---|-------------------|--------------------|---------|-----------------------------------------------------------------|
| 1 | Клієнт → сервер   | `[S]`              | SYN     | Клієнт ініціює з'єднання та передає свій початковий `seq`.      |
| 2 | Сервер → клієнт   | `[S.]`             | SYN-ACK | Сервер погоджується на з'єднання: свій `SYN` + `ACK` (`ack` = `seq` клієнта + 1). |
| 3 | Клієнт → сервер   | `[.]`              | ACK     | Клієнт підтверджує відповідь сервера (`ack` = `seq` сервера + 1). |

У `tcpdump` символ `.` означає прапорець ACK, тому `[S.]` = SYN + ACK. Фактична послідовність: `[S]` → `[S.]` → `[.]`.

Чи відбувся успішний TCP handshake? Так. У перехопленні присутні всі три пакети `[S]`, `[S.]`, `[.]` в одному й тому самому з'єднанні (однакова пара «IP:порт»). Підтвердження:

- сервер відповів `[S.]` — отже, порт 80 відкритий і сервер приймає з'єднання;
- значення `ack` у кожному пакеті на одиницю більше за `seq` попереднього пакета протилежної сторони;
- після рукостискання клієнт надіслав HTTP-запит, а `curl` отримав `HTTP/1.1 200 OK`.

Для порівняння: якщо в захопленні лише повторювані `[S]` без відповіді — сервер недоступний або пакети відкидає фаєрвол; якщо у відповідь приходить `[R.]` — порт закритий.

Прапорець `[P.]` — це комбінація прапорців PSH + ACK:

- P (PSH, Push) — відправник просить одержувача не затримувати дані в буфері, а негайно передати їх застосунку. Зазвичай ставиться на пакетах, що несуть корисне навантаження (дані прикладного рівня);
- . (ACK) — підтвердження отримання попередніх даних.

У нашому захопленні `[P.]` з'являється в пакетах з даними: у запиті клієнта (`GET / HTTP/1.1`) та у відповіді сервера (`HTTP/1.1 200 OK`). Прапорець `[P.]` не є ознакою помилки чи атаки — це нормальна частина передавання даних через TCP. Після обміну даними сторони підтверджують отримання пакетами `[.]`, а з'єднання закривається пакетами з прапорцем `[F.]` (FIN + ACK).

**Висновок до завдання 1:** `tcpdump` показав встановлення з'єднання, обмін даними та початок закриття: тристороннє рукостискання `[S] → [S.] → [.]`, передавання HTTP-даних з прапорцями `[P.]` та закриття з'єднання.

### Завдання 2. Налаштування Reverse Proxy (Nginx)

Конфігурація:

```nginx
location /api {
    proxy_pass http://localhost:3000;
    proxy_set_header X-Real-IP $remote_addr;
}
```

Директива `proxy_set_header X-Real-IP $remote_addr;` записує IP-адресу справжнього клієнта (змінна `$remote_addr`, яку бачить Nginx) у HTTP-заголовок `X-Real-IP` і передає його бекенду. Без неї бекенд встановлює TCP-з'єднання не з клієнтом, а з Nginx. У цій конфігурації Nginx і бекенд працюють на одному хості (`localhost`), тому як адресу відправника бекенд бачитиме `127.0.0.1` для всіх запитів. Наслідки:

- у журналах бекенда всі запити виглядатимуть так, ніби надходять з однієї адреси;
- не працюватимуть обмеження частоти запитів (rate limiting) та чорні/білі списки за IP;
- неможливо коректно розслідувати інциденти безпеки та визначати геолокацію;
- виявлення підозрілої активності (брутфорс, сканування) за IP стає марним.

Застереження: Nginx перезаписує заголовок `X-Real-IP` значенням `$remote_addr`, тому клієнт не може підробити його через Nginx. Але якщо порт 3000 доступний напряму з інтернету, зловмисник може обійти проксі й самостійно надіслати будь-який `X-Real-IP`. Тому бекенд повинен довіряти цьому заголовку лише від довіреного проксі, а порт 3000 має бути недоступним ззовні.

Розширений варіант конфігурації (за потреби):

```nginx
location /api {
    proxy_pass http://localhost:3000;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Основна перевага `proxy_pass` — зменшення поверхні атаки: ззовні доступний лише Nginx (порти 80/443), а бекенд приховано у внутрішній мережі. Усі запити проходять через проксі, на якому можна централізовано:

- завершувати HTTPS (TLS termination);
- обмежувати частоту запитів (`limit_req`) та розмір запитів;
- фільтрувати й блокувати підозрілі запити (у т. ч. підключити WAF);
- вести єдиний журнал доступу;
- приховати внутрішню архітектуру (адреси, порти, технології бекенда).

Але сам по собі `proxy_pass` порт 3000 не закриває. Щоб перевага справді працювала, бекенд потрібно прив'язати до loopback-інтерфейсу та/або закрити порт фаєрволом:

```bash
# приклад для Node.js: слухати лише локальний інтерфейс
# app.listen(3000, '127.0.0.1');

# перевірка: має бути 127.0.0.1:3000, а не 0.0.0.0:3000
ss -tlnp | grep 3000

# додатково — заборонити зовнішні підключення до порту 3000 (ufw)
sudo ufw deny 3000/tcp
```

**Висновок до завдання 2:** `X-Real-IP` зберігає інформацію про справжнього клієнта для бекенда, а Reverse Proxy разом із закритим портом 3000 централізує захист і зменшує поверхню атаки.

### Завдання 3. Вибір алгоритму балансування

**Обраний алгоритм: IP Hash**

Застосунок зберігає сесії в локальній пам'яті серверів (Stateful-архітектура), тому всі запити одного користувача мають потрапляти на той самий сервер, де створено його сесію. IP Hash обчислює хеш від IP-адреси клієнта й за ним обирає сервер, тож запити з однієї адреси стабільно йдуть на один бекенд («липкі» сесії, sticky sessions).

Приклад конфігурації Nginx:

```nginx
upstream app_backend {
    ip_hash;
    server 10.0.0.11:3000;
    server 10.0.0.12:3000;
}

server {
    listen 80;

    location / {
        proxy_pass http://app_backend;
    }
}
```

Round Robin розподіляє запити по черзі: A → B → A → B… Якщо користувач увійшов в систему на сервері A (сесія лежить у пам'яті A), то наступний запит потрапить на сервер B, де цієї сесії немає. Результат: користувача «розлогінює», кошик очищується, виникають помилки авторизації — додаток працює нестабільно.

Натомість Least Connections спрямовує запит на сервер з найменшою кількістю активних з'єднань. Цей алгоритм не враховує, де зберігається сесія користувача, тому має ту саму проблему, що й Round Robin: наступний запит може опинитися на іншому сервері.

IP Hash — не абсолютна гарантія:

- IP клієнта може змінитися (мобільна мережа, VPN);
- багато користувачів за одним NAT мають спільну IP-адресу, через що навантаження розподіляється нерівномірно (Nginx для IPv4 використовує перші три октети адреси);
- якщо сервер виходить з ладу, його клієнти переходять на інший сервер і втрачають сесії.

Надійніше рішення — винести сесії в спільне сховище (наприклад, Redis), тоді архітектура стає Stateless і підходить будь-який алгоритм балансування.

**Висновок до завдання 3:** для Stateful-архітектури обираємо IP Hash, бо він «прив'язує» клієнта до одного сервера; Round Robin і Least Connections такої прив'язки не дають.

### Завдання 4. Мікросегментація в Kubernetes

Повний маніфест політики (з обов'язковими полями `apiVersion`, `kind`, `metadata`):

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-backend-to-database
  namespace: default
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: backend
```

Застосування та перевірка:

```bash
kubectl apply -f networkpolicy.yaml
kubectl get networkpolicy
kubectl describe networkpolicy allow-backend-to-database
```

Поле `spec.podSelector` визначає Pod-и, до яких застосовується політика: це усі Pod-и з міткою `app: database` в тому самому namespace, де створено політику (NetworkPolicy діє в межах свого простору імен). Оскільки в політиці є секція `ingress`, значення `policyTypes` за замовчуванням включає `Ingress`. Це означає, що вибрані Pod-и стають ізольованими для вхідного трафіку: дозволене лише те, що явно описано в правилах.

Лише Pod-ам з міткою `app: backend` дозволено доступ до бази даних. Оскільки в `from` вказано тільки `podSelector`, вибираються Pod-и з цією міткою у тому самому namespace, що й політика. Усі інші вхідні з'єднання до Pod-ів `app: database` (наприклад, від Pod-ів `app: frontend`) блокуються, бо ці Pod-и ізольовані, а дозволу для інших джерел немає.

Додаткові зауваження:

- NetworkPolicy адитивні: якщо до Pod-а застосовано кілька політик, трафік дозволено, коли його дозволяє хоча б одна з них (об'єднання правил);
- у правилі не вказано `ports`, тому backend має доступ до всіх портів бази даних; за кращою практикою доступ варто обмежити конкретним портом (наприклад, `5432` для PostgreSQL);
- політика працює лише тоді, коли мережевий плагін (CNI) кластера підтримує NetworkPolicy (Calico, Cilium тощо).

Посилений варіант із обмеженням порту:

```yaml
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: backend
      ports:
        - protocol: TCP
          port: 5432
```

**Як це допомагає обмежити Blast Radius у разі злому фронтенда?**

Blast Radius — масштаб наслідків інциденту безпеки (скільки систем і даних може бути уражено після компрометації одного компонента). Якщо зловмисник захопить Pod фронтенда (`app: frontend`), він не зможе напряму підключитися до бази даних: його Pod не має мітки `app: backend`, тож трафік до `app: database` буде заблоковано. Мікросегментація:

- обмежує горизонтальне переміщення (lateral movement) зловмисника всередині кластера;
- зменшує кількість мережевих сервісів, доступних зі скомпрометованого Pod-а;
- реалізує принцип найменших привілеїв на мережевому рівні;
- перетворює «плоску» мережу, де всі бачать усіх, на сегментовану.

Обмеження: політика не захищає, якщо скомпрометовано сам backend-Pod, якому доступ дозволено. Тому потрібні також інші заходи: мінімальні права облікового запису БД, RBAC, секрети, моніторинг.

**Висновок до завдання 4:** політика ізолює Pod-и бази даних і пропускає до них лише `app: backend`, що суттєво зменшує Blast Radius у разі компрометації фронтенда.

### Завдання 5. Аналіз системи виявлення вторгнень (IDS)

Сповіщення Suricata:

```text
[Alert] ET EXPLOIT POSSIBLE SQL Injection (UNION SELECT)
```

Воно означає, що трафік збігся із сигнатурою можливої SQL-ін'єкції з використанням `UNION SELECT`. Це не доводить, що атака була успішною: для висновку потрібно проаналізувати сам запит, відповідь сервера, журнали застосунку та БД (можливі й хибні спрацювання).

**Що зробила б система IPS замість IDS?**

| Критерій            | IDS (Intrusion Detection System)                | IPS (Intrusion Prevention System)                     |
|---------------------|-------------------------------------------------|-------------------------------------------------------|
| Розміщення          | Пасивно (копія трафіку: SPAN/mirror-порт, TAP)  | Inline — трафік проходить крізь систему           |
| Дія                 | Виявляє та генерує сповіщення (alert)           | Виявляє й блокує (drop/reject)                    |
| Вплив на трафік     | Немає — пакет доходить до отримувача            | Є — підозрілий пакет не доходить до застосунку        |

Якби це була IPS, вона відкинула б пакет із запитом `UNION SELECT` (або розірвала відповідне з'єднання) ще до того, як він дійде до вебзастосунку. IDS лише зафіксувала б подію в журналі, а запит досягнув би сервера, і реагувати довелося б людині або іншій системі. Для порівняння, у Suricata різниця виражається дією правила (приклад-ілюстрація, не оригінальне правило ET):

```text
# IDS-режим: лише сповіщення
alert http any any -> $HOME_NET any (msg:"Example SQLi UNION SELECT"; flow:established,to_server; http.uri; content:"union"; nocase; content:"select"; nocase; distance:0; sid:1000001; rev:1;)

# IPS-режим (inline): блокування
drop http any any -> $HOME_NET any (msg:"Example SQLi UNION SELECT"; flow:established,to_server; http.uri; content:"union"; nocase; content:"select"; nocase; distance:0; sid:1000002; rev:1;)
```

Але IPS блокує лише тоді, коли Suricata запущено в inline-режимі, а правило має дію `drop`.

**Додатковий рівень Defense in Depth на рівні edge: WAF**

Web Application Firewall (WAF) на межі мережі (edge), перед вебзастосунком (наприклад, Cloudflare WAF, AWS WAF або ModSecurity з набором правил OWASP CRS). WAF аналізує HTTP/HTTPS-запити на рівні застосунку, розпізнає типові патерни SQL-ін'єкцій (`UNION SELECT`, `' OR 1=1` тощо) і блокує такий запит ще до того, як він потрапить у внутрішню мережу та до застосунку. Перевага над мережевою IDS/IPS: WAF завершує TLS і бачить розшифрований HTTP-трафік, тоді як IDS/IPS без розшифрування HTTPS не може перевірити вміст запиту.

Інші рівні захисту за концепцією Defense in Depth:

- валідація та нормалізація вхідних даних;
- параметризовані SQL-запити (найефективніший захист від SQL-ін'єкцій);
- мінімальні привілеї облікового запису БД;
- логування, моніторинг та оповіщення (SIEM);
- регулярне оновлення ПЗ.

Приклад небезпечного та безпечного коду (Python, `psycopg2`):

```python
# Небезпечно: введення користувача вставляється прямо в SQL
cur.execute(f"SELECT * FROM users WHERE id = {user_id}")

# Безпечно: параметризований запит — дані відокремлено від SQL-команди
cur.execute("SELECT * FROM users WHERE id = %s", (user_id,))
```

WAF — це додатковий рівень, а не заміна безпечної розробки: якщо один механізм пропустить атаку, наступний рівень має її зупинити.

**Висновок до завдання 5:** IDS лише повідомляє про підозрілий трафік, IPS додатково блокує його, а WAF на edge, параметризовані запити та моніторинг разом утворюють багаторівневий захист.

### Загальний висновок

У роботі розглянуто інструменти діагностики та захисту мереж:

- `tcpdump` дозволяє «бачити» мережу на рівні пакетів і діагностувати TCP-з'єднання (`[S] → [S.] → [.]`, `[P.]`);
- Nginx Reverse Proxy з директивою `X-Real-IP` зберігає IP клієнта для бекенда й, за умови закритого порту 3000, зменшує поверхню атаки;
- IP Hash забезпечує «прив'язку» клієнтів до серверів у Stateful-архітектурі, але надійніше за все виносити сесії в Redis;
- Kubernetes NetworkPolicy реалізує мікросегментацію та обмежує Blast Radius;
- IDS/IPS і WAF разом із безпечною розробкою формують багаторівневий захист (Defense in Depth).

Комплексне застосування цих засобів зменшує поверхню атаки, обмежує наслідки компрометації та підвищує загальний рівень безпеки інфраструктури.
