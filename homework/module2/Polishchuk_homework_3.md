### Завдання 1. Аналіз HTTP-заголовків та статус-кодів

**Команда:**

```bash
curl -I http://example.com
```

**Результат:**

```text
HTTP/1.1 200 OK
Date: Sat, 17 Oct 2026 19:29:11 GMT
Content-Type: text/html; charset=utf-8
Connection: keep-alive
Server: cloudflare
Last-Modified: Tue, 13 Oct 2026 20:08:28 GMT
Allow: GET, HEAD
Accept-Ranges: bytes
Age: 4952
cf-cache-status: HIT
CF-RAY: a4c1b5ec8983c917-KBP
alt-svc: h3=":443"; ma=86400
```

**Команда:**

```bash
curl -I -L http://example.com
```

**Результат:**

```text
HTTP/1.1 200 OK
Date: Sat, 17 Oct 2026 19:29:26 GMT
Content-Type: text/html; charset=utf-8
Connection: keep-alive
Server: cloudflare
Last-Modified: Tue, 13 Oct 2026 20:08:28 GMT
Allow: GET, HEAD
Accept-Ranges: bytes
Age: 4968
cf-cache-status: HIT
CF-RAY: a4c1b64b9978ca38-KBP
alt-svc: h3=":443"; ma=86400
```

- **Статус-код:** `200 OK` — запит оброблено успішно, сервер повідомив, що ресурс доступний. Команда `curl -I` надсилає HEAD-запит, тому у відповіді лише заголовки, без тіла сторінки.
- **Location:** відсутній. Редиректу немає: сервер одразу відповів `200 OK` на запит по `http://`. Запуск із прапорцем `-L` (слідувати редиректам) це підтверджує: відповідь та сама, переходу на іншу адресу не було.
- **Протокол:** `HTTP/1.1` — версія вказана в першому рядку відповіді (`HTTP/1.1 200 OK`).
- `Server: cloudflare` — сайт працює за CDN Cloudflare.
- `cf-cache-status: HIT`, `Age: 4968` та `Age: 4952` — відповідь віддано з кешу CDN, а не з origin-сервера.
- `alt-svc: h3=":443"` — сервер повідомляє, що доступний і HTTP/3 (порт 443), але в цьому запиті використано HTTP/1.1.
- `Allow: GET, HEAD` — для цього ресурсу дозволені лише методи GET і HEAD.

#### Приклад сайту з редиректом

**Команда:**

```bash
curl -I http://github.com
```

**Результат:**

```text
HTTP/1.1 301 Moved Permanently
Content-Length: 0
Location: https://github.com/
```

- **Статус-код:** `301 Moved Permanently` — ресурс назавжди переїхав на іншу адресу.
- **Location:** `https://github.com/` — адреса, на яку сервер перенаправляє клієнта.
- **Чому відбувається редирект:** сайт примусово переводить користувача з незахищеного `http://` на захищений `https://`, щоб трафік був зашифрований.
- **Протокол:** `HTTP/1.1`

### Завдання 2. Робота з методами HTTP

Для тесту використано публічне тестове API **DummyJSON**.

**Команда:**

```bash
curl -i -X POST https://dummyjson.com/products/add \
  -H "Content-Type: application/json" \
  -d '{"title":"Test product","price":100}'
```

**Результат (скорочено):**

```text
HTTP/2 201
date: Sat, 17 Oct 2026 19:29:54 GMT
content-type: application/json; charset=utf-8
content-length: 45
server: cloudflare

{"id":195,"title":"Test product","price":100}
```

Статус-код успішного створення ресурсу: `201 Created` — ресурс створено. У тілі відповіді повернувся об'єкт із присвоєним `id: 195`. (DummyJSON лише імітує створення — запис реально не зберігається на сервері, тому повторний GET за цим `id` його не поверне.)

**Чим POST відрізняється від GET**

| Критерій | GET | POST |
|---|---|---|
| Призначення | Отримання ресурсу | Створення ресурсу / відправка даних на обробку |
| Де передаються дані | В URL (query string: `?a=1&b=2`) | В тілі запиту (body), наприклад JSON |
| Видимість даних | Видно в адресному рядку, історії браузера, логах серверів і проксі | Не потрапляють в URL, тому менше «світяться» в логах та історії (але без HTTPS так само читаються в мережі) |
| Обмеження на розмір | Обмежений довжиною URL | Практично немає (обмежує лише налаштування сервера) |
| Кешування | Кешується за замовчуванням (браузером, CDN, проксі) | За замовчуванням не кешується |
| Ідемпотентність | Ідемпотентний і безпечний (не змінює стан сервера) | Не ідемпотентний: повторний запит може створити ще один ресурс |
| Закладки / посилання | Можна зберегти в закладки та поділитись посиланням | Ні |

### Завдання 3. Перевірка TLS-сертифіката

**Команда:**

```bash
openssl s_client -connect cloudflare.com:443 -servername cloudflare.com
```

**Ключові фрагменти виводу:**

```text
depth=2 C = US, O = Google Trust Services LLC, CN = GTS Root R4
depth=1 C = US, O = Google Trust Services, CN = WE1
depth=0 CN = cloudflare.com
...
Certificate chain
 0 s:CN = cloudflare.com
   i:C = US, O = Google Trust Services, CN = WE1
   a:PKEY: id-ecPublicKey, 256 (bit); sigalg: ecdsa-with-SHA256
   v:NotBefore: Sep  5 22:29:39 2026 GMT; NotAfter: Dec  4 23:29:33 2026 GMT
 1 s:C = US, O = Google Trust Services, CN = WE1
   i:C = US, O = Google Trust Services LLC, CN = GTS Root R4
   a:PKEY: id-ecPublicKey, 256 (bit); sigalg: ecdsa-with-SHA384
   v:NotBefore: Dec 13 09:00:00 2023 GMT; NotAfter: Feb 20 14:00:00 2029 GMT
 2 s:C = US, O = Google Trust Services LLC, CN = GTS Root R4
   i:C = BE, O = GlobalSign nv-sa, OU = Root CA, CN = GlobalSign Root CA
   a:PKEY: id-ecPublicKey, 384 (bit); sigalg: RSA-SHA256
   v:NotBefore: Nov 15 03:43:21 2023 GMT; NotAfter: Jan 28 00:00:42 2028 GMT
...
subject=CN = cloudflare.com
issuer=C = US, O = Google Trust Services, CN = WE1
...
Server Temp Key: X25519, 253 bits
Verification: OK
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Verify return code: 0 (ok)
```

| Параметр | Значення |
|---|---|
| Хто видав сертифікат (Issuer) | `C = US, O = Google Trust Services, CN = WE1` (центр сертифікації Google Trust Services, проміжний CA «WE1») |
| Узгоджений протокол TLS | `TLSv1.3` |
| Cipher Suite | `TLS_AES_256_GCM_SHA384` |

**Додатково:**

- Subject: `CN = cloudflare.com`.
- Ланцюжок довіри: `cloudflare.com` → `WE1` → `GTS Root R4` → `GlobalSign Root CA` (кросс-підпис від GlobalSign потрібен для сумісності зі старими клієнтами).
- Термін дії серверного сертифіката: з 5 вересня 2026 до 4 грудня 2026.
- Ключ сервера: ECDSA, 256 біт (`id-ecPublicKey`), підпис `ecdsa-with-SHA256`.
- Обмін ключами: ephemeral X25519 (забезпечує Forward Secrecy).
- Результат перевірки: `Verify return code: 0 (ok)` — сертифікат валідний і довіряється системою.
- Опція `-servername` передає SNI, щоб сервер (за CDN) віддав сертифікат саме для потрібного домену.

Розшифровка шифру `TLS_AES_256_GCM_SHA384`: симетричне шифрування AES з 256-бітним ключем у режимі GCM (шифрування + автентифікація даних), хеш SHA-384 використовується в процедурі виведення ключів. У TLS 1.3 назва шифру не містить алгоритму обміну ключами (він узгоджується окремо, тут — X25519).

### Завдання 4. Аналіз безпеки Cookies

Для аналізу обрано сайт github.com, який встановлює cookie вже при першому відвідуванні (без входу в акаунт).

**Команда:**

```bash
curl -sS -D - -o /dev/null https://github.com | grep -i set-cookie
```

**Результат (значення `_gh_sess` скорочено):**

```text
set-cookie: _gh_sess=mHa18oRzyKzWlzxXX4h0...%3D%3D; path=/; HttpOnly; secure; SameSite=Lax
set-cookie: _octo=GH1.1.2043830665.1792265871; expires=Sun, 17 Oct 2027 19:37:51 GMT; domain=.github.com; path=/; secure; SameSite=Lax
set-cookie: logged_in=no; expires=Sun, 17 Oct 2027 19:37:51 GMT; domain=.github.com; path=/; HttpOnly; secure; SameSite=Lax
```

**Cookie та їхні атрибути**

| Cookie (ID) | HttpOnly | Secure | SameSite | Path / Domain | Термін життя |
|---|---|---|---|---|---|
| `_gh_sess` (ідентифікатор сесії) | Так | Так | `Lax` | `/` | Сесійна (немає `Expires`, видаляється після закриття браузера) |
| `_octo` | **Ні** | Так | `Lax` | `/`, `.github.com` | До 17.10.2027 (~1 рік) |
| `logged_in` (значення `no`) | Так | Так | `Lax` | `/`, `.github.com` | До 17.10.2027 (~1 рік) |

Основна cookie для аналізу — **`_gh_sess`**: це сесійний ідентифікатор, який зберігає стан користувача на сервері, і саме для таких cookie найважливіші атрибути безпеки. Вона має всі три захисні атрибути: `HttpOnly`, `Secure`, `SameSite=Lax`. cookie `_octo` не має `HttpOnly`, тобто доступна з JavaScript (`document.cookie`). Це припустимо, бо вона не містить даних автентифікації (це ідентифікатор для статистики/аналітики), і клієнтський код сайту може її читати. `_gh_sess` та `logged_in` мають `HttpOnly`.

Атрибут `HttpOnly` забороняє JavaScript доступ до cookie (вона недоступна через `document.cookie`). Це захищає від крадіжки cookie через XSS. Якщо зловмисник зуміє впровадити на сторінку шкідливий скрипт, той не зможе прочитати `_gh_sess` і відправити її на сервер атакуючого. Браузер, як і раніше, автоматично додає таку cookie до HTTP-запитів, але код сторінки її не бачить. (`HttpOnly` не усуває саму XSS-вразливість, скрипт усе ще може виконувати запити від імені користувача. Він лише не дає викрасти cookie)

Атрибут `Secure` забороняє браузеру надсилати cookie через незахищене HTTP-з'єднання: вона передається лише по HTTPS. Роль цього атрибута — захист від перехоплення cookie в мережі. Без нього, якщо користувач відкриє хоча б один запит до сайту по `http://` (наприклад, у публічній Wi-Fi мережі), cookie піде відкритим текстом, і зловмисник, який прослуховує трафік, зможе її прочитати. Для сесійної cookie це означає викрадення сесії: атакуючий підставить вкрадений ідентифікатор і діятиме від імені користувача без пароля. З `Secure` браузер не відправить cookie по HTTP, тож перехоплювати нічого.

Атрибут `SameSite=Lax` обмежує надсилання cookie у міжсайтових запитах: cookie передається лише при переході за посиланням верхнього рівня з безпечним методом (наприклад, GET) і не передається, скажімо, у POST-формі з іншого сайту. Це знижує ризик CSRF-атак.

### Завдання 5. Архітектурне моделювання (Кейс)

Система: онлайн-біржа, ціни на акції змінюються щосекунди, а внутрішні сервіси (білінг та облік акцій) мають спілкуватися з мінімальною затримкою.

### Сценарій А. Оновлення графіків цін у браузері в реальному часі

Обраний протокол: WebSocket (захищений варіант `wss://`).

**Обґрунтування:**

1. Постійне двостороннє з'єднання. Після початкового HTTP-handshake (`Upgrade: websocket`, відповідь `101 Switching Protocols`) з'єднання залишається відкритим, і сервер сам пушить оновлення цін, не чекаючи запиту від клієнта.
2. Мала затримка та накладні витрати. У класичного HTTP-запиту на кожне оновлення йдуть повні заголовки, нове з'єднання або цикл «запит-відповідь». У WebSocket після встановлення з'єднання кожне повідомлення має заголовок лише в кілька байтів.
3. Усуває polling. Якщо опитувати сервер кожну секунду через HTTP (polling / long polling), це створює зайве навантаження на сервер і мережу, а дані приходять із запізненням.
4. Двосторонній обмін. Користувач може динамічно підписуватись і відписуватись на різні тікери, змінювати інтервал графіка, надсилати команди через те саме з'єднання.
5. Підтримка в усіх браузерах (нативний `WebSocket` API).

**Альтернативи:**

- Server-Sent Events (SSE) підходить, якщо потрібен лише потік «сервер → клієнт» (він простіший і працює поверх звичайного HTTP з автоматичним перепідключенням). Але для біржі зручніший двосторонній канал.
- HTTP polling — найгірший варіант: велика затримка та навантаження.

### Сценарій Б. Взаємодія між внутрішніми мікросервісами (білінг ↔ облік акцій)

Обраний протокол: gRPC (поверх HTTP/2, серіалізація Protocol Buffers).

**Обґрунтування:**

1. Бінарний формат Protobuf. Повідомлення компактніші та швидше серіалізуються/десеріалізуються, ніж текстовий JSON, що зменшує затримку та навантаження на CPU.
2. HTTP/2. Мультиплексування багатьох запитів в одному TCP-з'єднанні, стиснення заголовків (HPACK), довготривалі з'єднання, тож немає накладних витрат на відкриття нового з'єднання для кожного виклику.
3. Строга типізація та контракт. `.proto`-файл задає схему повідомлень і сервісів, із нього генерується код для різних мов. Для фінансових операцій (білінг, облік акцій) це важливо: менше помилок у форматі даних.
4. Підтримка стрімінгу (server/client/bidirectional streaming) для потоків подій між сервісами.
5. Вбудовані дедлайни / таймаути, автентифікація (TLS/mTLS), зручна інтеграція з service mesh і балансувальниками.

**Альтернативи:**

- REST + JSON поверх HTTP/1.1 — простіше й універсальніше, але текстовий формат, більші заголовки та повільніша серіалізація, що гірше за затримкою для внутрішнього «гарячого» шляху.
- Брокер повідомлень (Kafka, NATS, RabbitMQ) — доречний для асинхронних подій (наприклад, журнал угод, сповіщення), але для синхронних запитів «білінг ↔ облік» з низькою затримкою gRPC підходить краще. На практиці ці підходи комбінують.

### Підсумкова таблиця

| Сценарій | Протокол | Головна причина вибору |
|---|---|---|
| А. Графіки цін у браузері | WebSocket (`wss://`) | Постійний двосторонній канал, сервер пушить дані без polling |
| Б. Білінг ↔ облік акцій | gRPC (HTTP/2 + Protobuf) | Бінарний формат, мультиплексування, мінімальна затримка, чіткий контракт |

### Висновки

- Під час роботи за допомогою `curl` проаналізовано статус-коди, заголовки та версію протоколу HTTP, розібрано відмінність методів GET і POST.
- За допомогою `openssl s_client` переглянуто ланцюжок TLS-сертифікатів, видавця, версію TLS та шифронабір.
- Розглянуто атрибути безпеки cookies (`HttpOnly`, `Secure`, `SameSite`) і те, від яких атак вони захищають.
- Для кейсу біржі обрано WebSocket для оновлення цін у браузері та gRPC для комунікації між внутрішніми мікросервісами.
