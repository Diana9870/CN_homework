## Домашнє завдання №2

### Завдання 1. Аналіз відкритих портів 

Для перегляду TCP- та UDP-сокетів, які прослуховують адреси або очікують на обробку пакетів, використано команду:

```bash
ss -tuln
```

Пояснення: -t — TCP, -u — UDP, -l — лише сокети, що очікують з'єднання, -n — числові адреси та порти без перетворення на імена.

Результат виконання команди:

```
Netid        State         Recv-Q         Send-Q                  Local Address:Port                 Peer Address:Port        Process        
udp          UNCONN        0              0                          127.0.0.54:53                        0.0.0.0:*                          
udp          UNCONN        0              0                       127.0.0.53%lo:53                        0.0.0.0:*                          
udp          UNCONN        0              0                      10.255.255.254:53                        0.0.0.0:*                          
udp          UNCONN        0              0                           127.0.0.1:323                       0.0.0.0:*                          
udp          UNCONN        0              0                               [::1]:323                          [::]:*                          
tcp          LISTEN        0              4096                    127.0.0.53%lo:53                        0.0.0.0:*                          
tcp          LISTEN        0              4096                       127.0.0.54:53                        0.0.0.0:*                          
tcp          LISTEN        0              4096                          0.0.0.0:22                        0.0.0.0:*                          
tcp          LISTEN        0              1000                   10.255.255.254:53                        0.0.0.0:*                          
tcp          LISTEN        0              4096                             [::]:22                           [::]:* 
```

За результатами виконання команди визначено такі порти:

| Протокол | Порт | Адреса                                          | Стан   | Призначення                                                                 |
| -------- | ---: | ----------------------------------------------- | ------ | --------------------------------------------------------------------------- |
| TCP      |   22 | `0.0.0.0`, `[::]`                               | LISTEN | SSH — віддалений доступ                                                     |
| TCP      |   53 | `127.0.0.53%lo`, `127.0.0.54`, `10.255.255.254` | LISTEN | DNS — обробка запитів доменних імен                                         |
| UDP      |   53 | `127.0.0.53%lo`, `127.0.0.54`, `10.255.255.254` | UNCONN | DNS — обробка запитів без встановлення з'єднання                            |
| UDP      |  323 | `127.0.0.1`, `[::1]`                            | UNCONN | Зазвичай — порт керування chronyd для утиліти `chronyc` (лише localhost)    |

**Пояснення результатів:**

* TCP 22 — порт, який використовується протоколом SSH для віддаленого керування системою. Адреси `0.0.0.0` та `[::]` означають прослуховування на всіх IPv4- та IPv6-інтерфейсах відповідно.
* TCP 53 та UDP 53 — порти, пов'язані з DNS. DNS перетворює доменні імена на IP-адреси. Для UDP у виведенні `ss` використовується стан `UNCONN`, оскільки UDP не встановлює з'єднання так, як TCP.
* UDP 323 — порт, який зазвичай використовує служба chrony (chronyd) для прийому команд від утиліти `chronyc`. Сокет слухає лише на `127.0.0.1` та `[::1]`, тобто доступний тільки локально. Сам протокол NTP працює на UDP 123, тож порт 323 не є портом синхронізації часу як такої.

**Висновок до завдання:** за допомогою `ss -tuln` визначено порти, на яких система очікує з'єднання або пакети, їхні адреси, стани й призначення. Результати показують, що система використовує мережеві служби SSH і DNS; окремо є локальний UDP-сокет на порту 323

### Завдання 2. Визначення процесів, що використовують порти 

Для перегляду мережевих сокетів разом із процесами, які їх використовують, виконано команду з `sudo`, оскільки без підвищених прав ім'я процесу могло б не відображатися:

```bash
sudo ss -tulpn
```

Результат виконання команди:

```
Netid    State      Recv-Q     Send-Q          Local Address:Port         Peer Address:Port    Process                                       
udp      UNCONN     0          0                  127.0.0.54:53                0.0.0.0:*        users:(("systemd-resolve",pid=155,fd=16))    
udp      UNCONN     0          0               127.0.0.53%lo:53                0.0.0.0:*        users:(("systemd-resolve",pid=155,fd=14))    
udp      UNCONN     0          0              10.255.255.254:53                0.0.0.0:*                                                     
udp      UNCONN     0          0                   127.0.0.1:323               0.0.0.0:*                                                     
udp      UNCONN     0          0                       [::1]:323                  [::]:*                                                     
tcp      LISTEN     0          4096            127.0.0.53%lo:53                0.0.0.0:*        users:(("systemd-resolve",pid=155,fd=15))    
tcp      LISTEN     0          4096               127.0.0.54:53                0.0.0.0:*        users:(("systemd-resolve",pid=155,fd=17))    
tcp      LISTEN     0          4096                  0.0.0.0:22                0.0.0.0:*        users:(("systemd",pid=1,fd=66))              
tcp      LISTEN     0          1000           10.255.255.254:53                0.0.0.0:*                                                     
tcp      LISTEN     0          4096                     [::]:22                   [::]:*        users:(("systemd",pid=1,fd=67))
```

За отриманими результатами визначено такі процеси:

| Процес            | PID | Протокол | Порт | Призначення               |
| ----------------- | --: | -------- | ---: | ------------------------- |
| `systemd-resolve` | 155 | TCP      |   53 | DNS-резолвер              |
| `systemd-resolve` | 155 | UDP      |   53 | DNS-резолвер              |
| `systemd`         |   1 | TCP      |   22 | Прослуховування SSH-порту |

**Пояснення результатів:**

* Процес `systemd-resolve` (PID 155) — це служба `systemd-resolved`. Утиліта `ss` показує назву процесу, обрізану до 15 символів, тому остання літера «d» не відображається. Ця служба обслуговує DNS-сокети на порту 53.
* `systemd` з PID 1 прослуховує TCP-порт 22. Це може бути пов'язано з механізмом socket activation, коли systemd приймає з'єднання та за потреби запускає відповідну службу (наприклад, sshd).
* Навіть із `sudo` стовпець процесу порожній для сокетів `10.255.255.254:53` (TCP і UDP) та UDP 323 (на `127.0.0.1` і `[::1]`). Це означає, що ім'я процесу для них не вдалося визначити за наведеним результатом. Для адреси `10.255.255.254` це узгоджується з особливостями мережевої інфраструктури WSL, однак сам по собі порожній стовпець процесу не доводить, що сокет належить саме інфраструктурі WSL.

**Висновок до завдання:** команда `sudo ss -tulpn` дала змогу пов'язати частину мережевих портів із конкретними процесами та їхніми PID. Це допомагає визначити, які служби використовують мережеві ресурси системи.

### Завдання 3. Перевірка TCP-з'єднання

Для перевірки доступності TCP-порту 80 домену `google.com` використано команду:

```bash
nc -vz google.com 80
```

**Отриманий результат:**

```text
Connection to google.com (142.250.109.102) 80 port [tcp/http] succeeded!
```

**Аналіз результату:**

* Тип з'єднання: TCP.
* Порт: 80 (HTTP).
* Результат: з'єднання встановлено (`succeeded`).
* IP-адреса, до якої встановлено з'єднання: `142.250.109.102`.

TCP використовує триетапне встановлення з'єднання (three-way handshake): SYN → SYN-ACK → ACK.

**Висновок до завдання:** перевірка підтвердила можливість встановлення TCP-з'єднання з адресою, отриманою для `google.com`, на порт 80 у момент виконання команди. Це не гарантує доступність усіх HTTP-ресурсів сервера.

### Завдання 4. Порівняння TCP та UDP

Для порівняння виконано дві команди перевірки порту 53 DNS-сервера `8.8.8.8`.

**Перевірка UDP:**

```bash
nc -u -vz 8.8.8.8 53
```

Результат:

```text
Connection to 8.8.8.8 53 port [udp/domain] succeeded!
```

**Перевірка TCP:**

```bash
nc -vz 8.8.8.8 53
```

Результат:

```text
Connection to 8.8.8.8 53 port [tcp/domain] succeeded!
```

**Порівняльна таблиця**

| Характеристика            | TCP                                                             | UDP                                                           |
| ------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------- |
| Тип протоколу             | З орієнтацією на з'єднання                                      | Без встановлення з'єднання                                    |
| Встановлення з'єднання    | Виконується триетапне рукостискання                             | Не виконується                                                |
| Підтвердження доступності | Успішне з'єднання підтверджує можливість встановлення TCP-сесії | Успіх команди `nc` не гарантує, що віддалений сервіс відповів |
| Надійність передавання    | Забезпечує підтвердження та повторне передавання в межах TCP    | Не гарантує доставку або повторне передавання                 |
| Результат перевірки       | `succeeded`                                                     | `succeeded`                                                   |

**Різниця в поведінці:** TCP встановлює сесію, і результат `succeeded` підтверджує, що рукостискання завершилося успішно. UDP сесію не встановлює, тому `succeeded` для UDP не означає, що DNS-сервер обов'язково відповів на запит. Команда `nc -u -z` повідомляє про помилку лише тоді, коли надходить ICMP-повідомлення «port unreachable». Якщо такого повідомлення немає, вивід залишається `succeeded`, навіть якщо сервіс не відповідає. Для повноцінної перевірки DNS можна використати `nslookup` або `dig`.

**Висновок до завдання:** TCP забезпечує встановлення з'єднання та надійне передавання даних, тоді як UDP передає датаграми без встановлення сесії. Тому результати перевірки UDP потрібно інтерпретувати обережніше.

### Завдання 5. Перевірка DNS-резолвінгу (`nslookup cloudflare.com`)

Для перевірки перетворення доменного імені `cloudflare.com` на IP-адреси використано команду:

```bash
nslookup cloudflare.com
```

**Отримані результати:**

```text
Server:         10.255.255.254
Address:        10.255.255.254#53

Non-authoritative answer:
Name:   cloudflare.com
Address: 104.16.132.229
Name:   cloudflare.com
Address: 104.16.133.229
Name:   cloudflare.com
Address: 2606:4700::6810:84e5
Name:   cloudflare.com
Address: 2606:4700::6810:85e5
```

**Підсумок DNS-запиту**

| Параметр         | Значення                                       |
| ---------------- | ---------------------------------------------- |
| Домен            | `cloudflare.com`                               |
| DNS-сервер       | `10.255.255.254`                               |
| Порт DNS-сервера | 53                                             |
| IPv4-адреси      | `104.16.132.229`, `104.16.133.229`             |
| IPv6-адреси      | `2606:4700::6810:84e5`, `2606:4700::6810:85e5` |

**Аналіз результату:**

DNS-резолвер `10.255.255.254` повернув IPv4- та IPv6-адреси для домену `cloudflare.com`. Це означає, що доменне ім'я було успішно розв'язане в IP-адреси. У середовищі WSL адреса `10.255.255.254` може використовуватися як внутрішній DNS-резолвер, який пересилає запити до інших DNS-серверів. Рядок `Non-authoritative answer` означає, що відповідь отримано через звичайний рекурсивний резолвер, а не безпосередньо від авторитативного сервера домену.

**Висновок до завдання:** перевірка підтвердила успішне DNS-розв'язання домену `cloudflare.com` та отримання IPv4- й IPv6-адрес.

### Загальний висновок

Під час практичної роботи було досліджено мережеві порти та служби в середовищі Linux/WSL, визначено процеси, пов'язані з окремими мережевими сокетами, перевірено встановлення TCP-з'єднання, порівняно поведінку TCP і UDP та виконано DNS-резолвінг. Команди `ss -tuln` і `ss -tulpn` допомагають аналізувати мережеві сокети та процеси, які їх використовують. Команда `nc` дає змогу перевірити можливість мережевого з'єднання, а `nslookup` — перевірити перетворення доменного імені на IP-адреси. Отже, робота продемонструвала практичні способи діагностики мережевих служб і відмінності між TCP, UDP та DNS у Linux/WSL.
